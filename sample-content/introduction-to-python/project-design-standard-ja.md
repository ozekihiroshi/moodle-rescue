# Python実践課題の設計標準

この文書は、完成した1.7「週間サポート報告」と2.4「CSV図書記録管理」から、次の実践課題にも再利用できる設計原則を抽出したものです。特定の題材をコピーするのではなく、学習者が課題を理解し、自分で実装し、自分で正しさを確認して、成果物を提出できるまでの構造を共通化します。

## 1. 完成した課題に共通する構造

| 段階 | 学習者が理解すること | 教材が用意するもの |
|---|---|---|
| 1. 状況 | 誰が、何に困っているか | 短く具体的な業務・生活上の場面 |
| 2. 入力 | 元になる情報がどこにあり、どう渡されるか | 手入力値、配布ファイル、固定された更新指示など |
| 3. 成果物 | 何を作り、どのファイルを編集するか | 編集対象を一つに絞ったスターター |
| 4. 処理 | 入力から出力へ何を行うか | 順序の分かる処理一覧と公開仕様 |
| 5. 結果 | 完成すると何が表示・保存されるか | 動作確認用データと期待結果 |
| 6. 自己確認 | 自分の目で何を確かめるか | 実行コマンドと照合値 |
| 7. 自動確認 | ロジックが仕様どおりか | 変更禁止の確認プログラムと明確な診断 |
| 8. 提出 | 何をどこへ提出するか | 単一成果物、提出方法、完了表示 |

この順序によって、学習者は次の流れを頭の中に描けます。

> 課題を理解する → 入力を確認する → スターターを完成させる → 自分で実行する → 確認プログラムを通す → 成果物を提出する

## 2. 1.7と2.4から抽出した不変部分

### 課題の入口

冒頭では、プログラムの条件より先に問題の場面を説明します。最低限、次の四点を一続きの文章で示します。

1. 誰が使うのか。
2. 現在どのような手作業や問題があるのか。
3. プログラムへ何を渡すのか。
4. プログラムから何を得るのか。

「データがあります」「集計してください」だけでは課題になりません。入力の所在と受け渡し方が分かって初めて、学習者は作業を始められます。

### 編集対象

学習者が最初に知るべき操作は、編集するファイルです。次の形式で明記します。

- Pythonプログラムを一から作るのか、スターターを完成させるのか。
- 編集するファイルの名前とPython Lab内の場所。
- 変更してはいけない確認プログラムや入力原本。
- 提出するファイルと、提出しないファイル。

原則として一つの課題で提出するプログラムは一つにします。Notebookは作業案内、確認プログラムは自己採点、入力データは原本であり、成果物とは区別します。

### 入力データの契約

入力について、次のどれかを必ず確定します。

- 実行時にキーボードから入力する。
- 配布ファイルから読み込む。
- スターター内の定数または指定された関数呼出しとして与える。
- 学習者が条件に従って自分で作る。

サンプルデータを示す場合は、それが入力例、動作確認用、原本、期待出力のどれなのかを明記します。ファイルなら、パス、形式、文字コード、列、保護すべき原本、出力先を示します。

### 公開仕様

確認プログラムが要求する条件は、すべて学習者へ公開します。公開仕様には必要に応じて次を含めます。

- 入力順と入力形式
- 出力項目、表記、順序
- 計算・判定規則と境界値
- 同率、0件、空データ、不正値の扱い
- 関数名、引数、戻り値、状態変化、例外
- ファイル名、列順、並び順、保存先
- 使用できる、またはまだ使用しないPythonの範囲

確認プログラムだけが知っている隠れた条件を作りません。実装方法を限定する場合は、「業務ルール」ではなく「学習上の実装条件」として区別します。

### スターターの役割

スターターは答えを隠すための空欄集ではなく、学習者を実装順へ導く足場です。

- 未学習の環境設定やパス処理は完成済みにする。
- TODOを処理の順番に配置する。
- 一つのTODOへ複数の大きな判断を詰め込まない。
- 最初の実行では、未完成であることを明確に表示する。
- 章で未学習の構文を要求しない。
- 完成後に削除する行を明示する。

### 二段階の確認

最初に学習者自身が、公開されたサンプルを入力して結果を読みます。その後に確認プログラムを実行します。

確認プログラムの目的は採点の威圧ではなく、学習者が自分で修正できることです。

- 正常系だけでなく、境界値とよくある誤りを確認する。
- `OK`または`NG`を項目単位で示す。
- `NG`では、見直す関数・項目、期待値、実際値を可能な範囲で示す。
- 未完成スターターでは大量の失敗を出さず、最初の作業を案内する。
- 全項目合格時は`ALL TESTS PASSED`のような明確な完了表示を出す。
- 確認プログラム自体の理解や変更を、まだ学習目標に含めない。

### 提出と記録

提出前に保存操作を明記します。確認と提出は、エディター上の未保存内容ではなく保存済みファイルを使います。

- 提出対象は一つに限定する。
- 自動確認不合格時は提出しない。
- 直接提出が失敗した場合は成功表示を出さない。
- 直接提出とMoodle標準アップロードの両方を利用可能にできる。
- Moodleを提出済み成果物の記録場所とし、教師がPython Labの個人領域を見ることを前提にしない。
- 再提出時の扱いを説明する。

## 3. 課題ごとに変える部分

| 設計項目 | 1.7 | 2.4 | 次の課題で決めること |
|---|---|---|---|
| 課題規模 | 章前半の小プロジェクト | 章末の統合プロジェクト | 学習時間と統合する概念数 |
| 入力 | 日報を見ながら10個を手入力 | 配布CSVを読み込む | 入力の所在と渡し方 |
| 主な処理 | 合計、率、判定、最大値 | 読込、検索、更新、集計、保存 | 章の到達内容から逆算 |
| 実装単位 | 逐次処理と一つのループ | 公開仕様のある10関数 | 学習済みの抽象化レベル |
| 出力 | 画面の週間報告 | 画面報告と更新CSV | 利用者が必要とする成果 |
| 異常系 | 負数、解決超過、0件 | CSV不備、重複、空欄、対象なし | 現実に起きる代表的な誤り |
| 自動確認 | ブラックボックスで8場面 | 関数単体と統合で10項目 | 公開仕様と一対一対応する検査 |

題材を先に決めて学習内容を押し込むのではなく、「この章までに何を学んだか」と「その知識で自然に解ける問題」の交点から課題を選びます。

## 4. 次の課題を作る順序

1. **学習範囲を固定する。** その課題以前に学習済みの構文、標準ライブラリ、データ形式を列挙します。
2. **解決する問題を一文で定義する。** 「誰の、どの作業を、どの入力から、どの成果へ変えるか」を書きます。
3. **期待成果を先に作る。** サンプル入力、期待出力、保存ファイルを手計算または参照実装で確定します。
4. **公開仕様を確定する。** 境界値、異常系、関数契約、パス、表記を決めます。
5. **確認項目を作る。** 各項目を公開仕様の一つ以上へ対応付けます。仕様にない検査は禁止します。
6. **参照実装を作る。** 全確認項目が通り、学習範囲外の近道を使っていないことを確認します。
7. **スターターへ戻す。** 参照実装から、学習者が考える部分だけをTODOへ戻します。
8. **課題文を書く。** 状況、入力、成果物、処理、結果、確認、提出の順に説明します。
9. **Notebookを作る。** ファイルを開く、保存する、手動実行する、自動確認する、提出する流れに限定します。
10. **学習者として通す。** スターターだけから完成できるか、コマンドとパスを含めて実際に操作します。
11. **失敗経路を通す。** 未完成、テスト不合格、接続失敗、再提出が誤解のない表示になることを確認します。
12. **配布物を同期する。** Moodle、Notebook、README、スターター、確認プログラム、参照実装の仕様を照合します。

## 5. 課題本文の標準構成

次の見出しを基本形とします。不要な見出しは削れますが、内容を暗黙にはしません。

1. 課題の状況
2. この課題で行うこと
3. 編集するファイルと提出物
4. 入力方法または入力データ
5. 処理・判定・関数の公開仕様
6. 期待される出力または保存結果
7. 異常な入力の扱い
8. 使用するPythonの学習範囲
9. 段階的な実装順とヒント
10. 手動確認
11. 自動確認
12. 保存・提出・完成条件

本文は上から下へ作業の順に読めるようにします。補足説明は、本文の流れを止めない短い注記、詳細表、折りたたみ式のヒントへ分離します。

## 6. 完成判定ゲート

次のすべてが満たされたとき、その課題を完成とします。

### 内容

- 初見の学習者が、入力の所在と作業開始点を説明できる。
- 章の学習内容だけでスターターを完成できる。
- サンプル入力から期待結果を手動で照合できる。
- 異常系と境界値が曖昧でない。

### ファイル

- Moodle、Notebook、READMEのファイル名とコマンドが一致する。
- スターターの関数名・TODO・パスが公開仕様と一致する。
- 確認プログラムが公開仕様にない条件を要求しない。
- 参照実装が全確認項目を通る。
- 入力原本や確認プログラムを学習者が変更する必要がない。

### 操作

- Python Labから手動実行できる。
- 未完成時の案内が理解できる。
- 自動確認の失敗箇所を学習者が特定できる。
- 合格した保存済み成果物だけを提出できる。
- Moodleで提出済みファイルを教師が確認できる。
- 再提出、接続失敗、未在籍などの経路が正しく扱われる。

### 配布

- 英語正本と日本語適応版で、ファイル名、仕様、確認項目が一致する。
- Notebook原本、生成先、配布イメージの内容が一致する。
- 既存学習者の編集済み成果物を更新処理で上書きしない。
- バックアップまたは復元可能な配布物を作成できる。

## 7. 次の課題で最初に埋める設計票

次の課題では、本文やコードを書く前に以下を埋めます。

```text
課題名：
位置付け（章・小課題／章末／卒業）：
この時点で学習済みの内容：

利用者：
現在の問題：
入力の所在：
プログラムへの渡し方：
必要な出力・保存物：

編集するファイル：
提出するファイル：
変更しないファイル：

正常系のサンプル入力：
期待結果：
境界値：
異常系：

公開する実装条件：
実装の段階：
自動確認項目：
完成時の表示：

手動実行コマンド：
自動確認コマンド：
提出方法：
```

この設計票、参照実装、確認項目を先に完成させてから、スターター、課題本文、Notebookを作ります。これにより、説明を後から継ぎ足して矛盾を修正するのではなく、最初から解けて確認できる課題を組み立てられます。
