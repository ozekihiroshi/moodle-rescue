## Introduction

**A real lending desk coordinates many objects.** An item knows whether it can be loaned, but it should not know every other item or how the inventory is searched. A coordinating class owns the collection while state rules remain with each item.

## Learning outcomes

- Store objects in a collection keyed by stable identity.
- Use composition to model a desk containing items.
- Delegate transitions to the object owning the rule.
- Derive summaries without a second source of truth.

**Learning route:** Required 4.3.1–4.3.4 \| Integration 4.3.5

## 4.3.1 Compose a desk from item objects

Composition means that one object contains or uses other objects. A dictionary keyed by item ID makes lookup and uniqueness explicit.

```
class LendingDesk:
    def __init__(self):
        self.items = {}

    def add_item(self, item):
        if item.item_id in self.items:
            raise ValueError("duplicate item ID")
        self.items[item.item_id] = item

    def find_item(self, item_id):
        return self.items.get(item_id.strip())

    def loan_item(self, item_id, borrower_id):
        item = self.find_item(item_id)
        if item is None:
            raise KeyError(item_id)
        item.loan_to(borrower_id)
```

The values are actual `EquipmentItem` objects, not copies of their attributes.

## 4.3.2 Put responsibility where the information lives

The desk answers “which item?” The item answers “is this transition allowed?” `loan_item` searches and then calls `item.loan_to()`. Repeating double-loan rules in both classes would create two versions that drift apart.

```
desk.loan_item("E001", "M014")
# desk: locate E001
# item: validate and change its own borrower
```

## 4.3.3 Distinguish absence from invalid state

An unknown ID means the object is absent, so the desk raises `KeyError`. An existing object that refuses a transition raises `ValueError`. This difference later becomes a useful audit message.

```
try:
    desk.loan_item("E999", "M014")
except KeyError:
    print("unknown item")

try:
    desk.loan_item("E002", "M014")
except ValueError:
    print("item cannot be loaned")
```

## 4.3.4 Derive collection results

Counts come from current item state. Storing a separate available total would require every transition to update two places.

```
def summary(self):
    available = sum(item.is_available() for item in self.items.values())
    return {
        "total_items": len(self.items),
        "available_items": available,
        "loaned_items": len(self.items) - available,
    }
```

## Integrated practice: a lighter rehearsal for the chapter project

**Connection to the chapter project:**

Build a small timetable that owns room reservations, keeping collection rules out of each reservation.

### What to build

Define `Schedule.add(reservation)`, `find(booking_id)`, and `count_by_status()`. Reject duplicate IDs. `Reservation` remains responsible only for one booking.

### Completion criteria

- `Schedule` contains a list of `Reservation` objects.

- Search by booking ID and return `None` when absent.

- The status count is a dictionary derived from current objects.

### Step-by-step guide

1.  Initialise the collection in `Schedule.__init__`.

2.  Call `find` before appending.

3.  Loop over reservations to build counts.

**Build and run your own version before opening the model answer.**

> **Model answer and explanation**
>
> ```
> class Reservation:
>     def __init__(self, booking_id, status="PENDING"):
>         self.booking_id = booking_id
>         self.status = status
>
>
> class Schedule:
>     def __init__(self):
>         self.reservations = []
>
>     def find(self, booking_id):
>         for reservation in self.reservations:
>             if reservation.booking_id == booking_id:
>                 return reservation
>         return None

>     def add(self, reservation):
>         if self.find(reservation.booking_id) is not None:

>     def count_by_status(self):

> ```

> Composition assigns one-record rules to `Reservation` and collection-wide rules to `Schedule`.

## Summary

After completing this lesson and its integrated practice, you can:

- Composition lets a coordinator own a collection of domain objects.
- Delegation keeps search, uniqueness, and transition rules in suitable places.
- Derived totals do not become stale stored state.
