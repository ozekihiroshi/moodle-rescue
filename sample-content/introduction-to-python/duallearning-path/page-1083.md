## Introduction

**Files contain records; a running program uses objects.** CSV cannot store methods. The program converts rows into objects, performs work through methods, then converts final objects back into rows. This explicit boundary preserves reusable rules and auditable files.

## Learning outcomes

- Convert CSV rows into domain objects and objects back into rows.
- Continue after expected rejection and retain one result per request.
- Keep orchestration separate from domain rules.
- Test with different data and protect source files.

**Learning route:** Required 4.4.1–4.4.5 \| Integration 4.4.6

## 4.4.1 Load rows by constructing objects

`DictReader` supplies strings. Construction applies the same cleaning and validation whether data came from a file or direct code.

```
def load_inventory(path):
    desk = LendingDesk()
    with Path(path).open(newline="", encoding="utf-8") as handle:
        for row in csv.DictReader(handle):
            item = EquipmentItem(
                row["item_id"], row["name"], row["category"], row["borrower_id"]
            )
            desk.add_item(item)
    return desk
```

Adding through the desk also applies duplicate-ID rules; loading does not bypass class contracts.

## 4.4.2 Convert one object to one storage row

`to_record()` is the reverse boundary. In-memory `None` becomes an empty CSV field. The method describes one row but does not open a file.

```
def to_record(self):
    return {
        "item_id": self.item_id,
        "name": self.name,
        "category": self.category,
        "borrower_id": self.borrower_id or "",
    }
```

## 4.4.3 Process requests and retain an audit result

An expected business rejection must not discard later requests. Catch only the published `ValueError` and `KeyError`, record REJECTED, and continue.

```
def process_requests(desk, path):
    results = []
    with Path(path).open(newline="", encoding="utf-8") as handle:
        for row in csv.DictReader(handle):
            try:
                if row["action"] == "LOAN":
                    desk.loan_item(row["item_id"], row["borrower_id"])
                elif row["action"] == "RETURN":
                    desk.return_item(row["item_id"])
                else:
                    raise ValueError("unknown action")
                status = "ACCEPTED"
            except (ValueError, KeyError):
                status = "REJECTED"
            results.append({"request_id": row["request_id"], "status": status})
    return results
```

Do not hide unexpected programming errors with a broad `except Exception`.

## 4.4.4 Orchestrate without duplicating rules

`run_project()` reads like the job: load, process, save final inventory, save results, derive counts. It connects tested units rather than reimplementing loan rules.

```
desk = load_inventory(inventory_path)
results = process_requests(desk, requests_path)
desk.save_inventory(inventory_output)
save_results(results, results_output)
```

## 4.4.5 Test with a second dataset and protect sources

A program containing answers for E001–E005 is not a solution. Use temporary X1/X2 records and a different request order. Check status, final state, output order, and unchanged source bytes.

```
before = inventory_path.read_bytes()
result = run_project(inventory_path, requests_path, out1, out2)
assert inventory_path.read_bytes() == before
assert result["accepted"] + result["rejected"] == result["requests"]
```

## Integrated practice: a lighter rehearsal for the chapter project

**Connection to the chapter project:**

Rehearse the class-to-CSV boundary with bicycle rentals rather than equipment loans.

### What to build

Give `Rental` a `to_record()` method and `from_record()` class method. Save two rentals to CSV, reload them, and assert that ID, bicycle ID, and active state survive the round trip.

### Completion criteria

- CSV rows contain strings; the object uses Boolean state.

- Serialisation belongs at the boundary, not scattered through business methods.

- The input and output headers remain stable.

### Step-by-step guide

1.  Write Boolean values as `true` or `false`.

2.  Parse them explicitly when loading.

3.  Compare attribute tuples after reopening.

**Build and run your own version before opening the model answer.**

> [!ANSWER]
> **Model answer and explanation**
>
> ```
> class Rental:
>     def __init__(self, rental_id, bicycle_id, active):
>         self.rental_id = rental_id
>         self.bicycle_id = bicycle_id
>         self.active = active
>
>     def to_record(self):
>         return {"rental_id": self.rental_id, "bicycle_id": self.bicycle_id,
>                 "active": "true" if self.active else "false"}
>
>     @classmethod
>     def from_record(cls, row):
>         value = row["active"].strip().lower()
>         if value not in {"true", "false"}:
>             raise ValueError("invalid active value")
>         return cls(row["rental_id"], row["bicycle_id"], value == "true")
>
> rental = Rental.from_record(Rental("R01", "B07", True).to_record())
> assert (rental.rental_id, rental.bicycle_id, rental.active) == ("R01", "B07", True)
> print("ROUND TRIP OK")
> ```
>
> **Representative check**
>
> ```
> ROUND TRIP OK
> ```
>
> Objects provide behaviour in memory; records provide portable persistence. Explicit conversion keeps both representations understandable.
