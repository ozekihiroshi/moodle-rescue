Introduction

Begin with a design that already works. Chapter 2 represented one record with a dictionary and passed it to functions. That design remains appropriate for a few passive records. Lending equipment has a changing borrower and several operations that must agree about the same state. We therefore compare both designs before deciding what a class improves.

Learning outcomes

  • Distinguish class, object, and instance in executable code.
  • Use __init__ and self to create independent objects.
  • Read attributes and method calls from the object on the left.
  • Decide whether a class or records plus functions better fits a small problem.
Learning route: Required 4.1.1–4.1.4 | Integration 4.1.5

4.1.1 Start with records and functions

The dictionary stores state and the function receives a record to change it. Run the program and locate data, operation, and caller.

item = {
    "item_id": "E001",
    "name": "Laptop 01",
    "category": "Computer",
    "borrower_id": None,
}

def loan_item(record, borrower_id):
    if record["borrower_id"] is not None:
        raise ValueError("already on loan")
    record["borrower_id"] = borrower_id

loan_item(item, "M014")
print(item["borrower_id"])

This version is short and clear. Its cost appears as loan, return, rename, validation, and saving functions all need knowledge of the same keys. A class is justified by related state and growing rules, not merely by the presence of data.

Quick check: If the record is read-only, what behaviour would a class actually organise?

4.1.2 Define construction and behaviour together

A class is a definition. Calling the class constructs an object; that particular object is an instance. __init__ establishes its initial attributes, while methods describe operations available to it.

class EquipmentItem:
    def __init__(self, item_id, name, category):
        self.item_id = item_id
        self.name = name
        self.category = category
        self.borrower_id = None

    def is_available(self):
        return self.borrower_id is None

    def loan_to(self, borrower_id):
        if not self.is_available():
            raise ValueError("already on loan")
        self.borrower_id = borrower_id

The class does not contain E001 or E002. It defines how any equipment item begins and how one item answers or changes state.

4.1.3 Read self as the receiving object

During first.loan_to("M014"), self is first. Every self.attribute access therefore refers to that receiver.

first = EquipmentItem("E001", "Laptop 01", "Computer")
second = EquipmentItem("E002", "Projector", "Presentation")

first.loan_to("M014")

print(first.borrower_id)   # M014
print(second.borrower_id)  # None

The second instance remains unchanged. This is the first practical benefit over a loose collection of shared variables: the call names the individual whose state is involved.

Calling EquipmentItem.loan_to(first, "M014") expresses the same dispatch explicitly, but normal code uses first.loan_to("M014").

4.1.4 Separate attributes, methods, equality, and identity

An attribute such as item.name stores state. A method such as item.is_available() asks for behaviour. Parentheses matter, but the deeper distinction is data versus an operation using the object.

a = EquipmentItem("E001", "Laptop 01", "Computer")
b = EquipmentItem("E001", "Laptop 01", "Computer")

print(a is b)                  # False
print(a.item_id == b.item_id)  # True

is asks whether two names refer to the same object. == asks whether values compare equal. Two separately created items may carry the same ID, although the lending desk will later reject that business-level duplicate.

4.1.5 Integrated practice: refactor and compare

Add display_label(), returning a label such as E001 — Laptop 01. Create two items and verify each label uses its own attributes. Then rewrite the same operation as a function receiving a dictionary. State which form is clearer for (a) one read-only record and (b) many items with loan and return rules.

Summary

  • A class defines construction and related behaviour; an instance is one object created from it.
  • self identifies the receiver, so instance attributes remain independent.
  • Classes are valuable when state and rules belong together, but are not automatically better for every record.
