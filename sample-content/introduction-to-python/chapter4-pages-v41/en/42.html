Introduction

An object is useful only while its state remains believable. A loan item cannot be available and assigned to a borrower at the same time. It cannot be loaned twice, and a rejected operation must leave it exactly as it was. This lesson places those rules where state changes.

Learning outcomes

  • Validate required attributes during construction.
  • State an invariant and identify the method responsible for it.
  • Reject invalid transitions before mutation.
  • Test successful and rejected transitions with assertions.
Learning route: Required 4.2.1–4.2.4 | Integration 4.2.5

4.2.1 Establish valid state during construction

The constructor is the first boundary. Strip surrounding whitespace and reject an empty ID, name, or category before a usable object exists.

def required(value, label):
    cleaned = value.strip()
    if not cleaned:
        raise ValueError(f"{label} must not be empty")
    return cleaned

self.item_id = required(item_id, "item_id")

Construction either completes with all required attributes or raises an exception. Do not leave a partly initialised object for later code to repair.

4.2.2 Express one invariant with one source of state

An invariant should remain true after every completed public operation. Here borrower_id is None means available; any non-empty borrower means on loan.

def is_available(self):
    return self.borrower_id is None

A separate available flag could contradict the borrower. Deriving availability keeps one source of truth.

4.2.3 Validate before changing state

Check every refusal condition before assignment. If an exception is raised, the previous borrower remains unchanged.

def loan_to(self, borrower_id):
    borrower_id = borrower_id.strip()
    if not borrower_id:
        raise ValueError("borrower_id must not be empty")
    if not self.is_available():
        raise ValueError("item is already on loan")
    self.borrower_id = borrower_id

def return_item(self):
    if self.is_available():
        raise ValueError("item is not on loan")
    self.borrower_id = None

Mutating first and validating second would corrupt the object even though the method eventually failed.

4.2.4 Test success, refusal, and preservation

Boundary bugs are missed by happy-path tests. Check before success, after success, and after rejection.

item = EquipmentItem("E001", "Laptop 01", "Computer")
assert item.is_available()
item.loan_to("M014")
try:
    item.loan_to("M021")
except ValueError:
    pass
else:
    raise AssertionError("double lending should fail")
assert item.borrower_id == "M014"

4.2.5 Integrated practice

Draw AVAILABLE and ON LOAN. Label the permitted transitions loan_to and return_item. Test valid loan, double loan, valid return, and return while already available. Confirm rejected calls preserve state.

Summary

  • Construction establishes valid initial state.
  • An invariant gives all transition methods one consistent rule.
  • Validation precedes mutation; refusal paths require tests too.
